# Year in numbers

Issue #1135 adds an admin-only report at `/dashboard/metrics/year-in-numbers`. It uses additive UTC-day counts, never sums rolling metrics, and never estimates missing calendar-year history. The current UTC day is excluded. There are no year-on-year comparisons.

Activity totals are always labelled **partial recorded activity**. Their defensible scope is the supported received rows available at daily snapshot time, not all successful product operations. Browser opt-outs, blocking, delivery loss, uninstrumented clients and prior raw-event erasure cause undercounting. Client instrumentation is not an authoritative transaction ledger; spoofed client events and anonymous staff/test activity cannot be fully excluded. Existing intake excludes signed-in admins and likely bots. A missing event is not proof an operation did not happen.

Supported event contracts are 1.0.0 and 1.1.0: the placement counts, session-attribution/meaningful-edit signals, export successes and share/view event definitions are unchanged for these metrics. They retain the existing per-contract intake deduplication; a client moving between versions may contribute again. Unversioned events are deliberately excluded. Do not describe the result as unique links, unique views or an exhaustive action total.

## Collection and recovery

Migration `0038_year_in_numbers.sql` creates the anonymous totals, records collection start and enables registration counting atomically. Migration `0039_year_number_account_history.sql` adds a one-time anonymous historical snapshot using creation dates of surviving non-admin accounts, for complete days from 2026-01-01 (bounded by 24-month retention) strictly before the collection-start UTC day. Deleted accounts and current admins are absent, so this is a lower bound, never verified full registration history. The snapshot is immutable: later deletion, role changes or backdated inserts do not rewrite it. The deployment day is excluded from registration reporting because its coverage is partial. No identities, per-account lookup table or individual registration ledger are created. Account opt-out does not gate the identifier-free registration counter; event analytics preferences continue to apply at intake.

The nightly product-event task runs `aggregateYearNumbers` **before** raw expiry. The existing admin “Run aggregation now” action also runs it. Admin callers can use `POST /api/dashboard/metrics/maintenance?scope=year-in-numbers` to refresh only this report, with the same authentication, capability and CSRF checks. This can refresh the annual report without also running rolling-metric backfill. A single SQL statement inserts all five event cells for each missing day. Rows are immutable on conflict, so retry/interruption, raw expiry, later opt-out and account deletion cannot subtract from or duplicate an already finalized anonymous event count. Registration counters update atomically with account creation; complete-day zeros are filled only after the collection-start day. A failed annual aggregation prevents that task from deleting raw events.

Event timestamps are assigned by the server, not supplied by the client. Each complete UTC day is finalized using the rows visible when maintenance runs. Historical events inserted manually or exceptionally late after finalization are not added retroactively. Current-day counts are never reported. The registration trigger uses database insertion time, so a backdated `createdAt` cannot change a closed registration day.

Backfill starts at the later of MTR-001's declared measurement start and the first wholly retained UTC day (today minus 179 days). The boundary day of the 180-day retention window can already have partially expired and is excluded. The first observed event is not used to infer measurement start. For 2026, retain the recoverable supported period and label the rest missing; neither surviving projects/shares nor rolling aggregates establish missing historical actions or deleted registrations. The separately labelled surviving-account snapshot provides only a historical registration lower bound. Inspect production coverage privately; do not commit or post internal production counts in issues/PRs. This feature does not itself run a production migration or backfill.

The report displays each metric's recorded interval, number of aggregated days versus expected completed days, and last source update. Gaps stay visible in recap text. Full completed-day registration coverage using only the atomic trigger is the only metric eligible for **verified for stated scope**; any interval containing the historical snapshot remains partial; it remains subject to its explicit insertion-time exclusions. All activity figures remain partial, even with every day aggregated. A missing or suppressed figure is an em dash, never a fabricated zero.

Active design sessions are deliberately anchored to the existing session-scoped acquisition event, not daily distinct-edit counts. The latter could count a long-running browser session again on subsequent days. Before finalizing the arrival day, require an existing supported meaningful-edit event for the same session, deduplicate attribution across supported versions, and exclude missing attribution. Edits received after the arrival day was finalized do not rewrite the anonymous count. This conservative undercount is disclosed in the definition. No new session identifier or linkable lookup table is retained. When the acquisition event expires, later edits alone cannot make the same session count again.

## Aggregate access and privacy review

Daily storage contains only day, metric, count, a capped contributor threshold (0–5), source category and update time. There are no item variants, paths, account/session/project/share identifiers, cross-dataset joins or lookup keys. The dashboard exposes annual totals only to admins; it does not expose daily cells or contribution details. The read-only recap preserves the source limitations and interval.

Apply the existing contract's five-contributor reporting rule conservatively: event totals become reportable only if at least one contributing UTC day has five distinct recorded actors (account ID when signed in, otherwise session ID). Daily distinct counts must not be summed into unique annual contributors. Registration totals require five account insertions across the selected complete-day rows. No exact low-volume count is exposed in the report or recap. These are account/session thresholds, not verified human identities. Thresholds and coarse dimensions reduce singling-out risk; changes to access, dimensions or external data require a fresh review under the existing product-metrics contract. Completed counts cannot be joined back to an individual in this dataset and are not rewritten on erasure. Anonymous rows expire after 24 months; therefore older annual intervals may eventually become partial/unavailable.

The English privacy notice describes anonymous registration totals, public annual summaries and 24-month retention. Terms are unchanged: the report adds no user obligation, licence or service restriction. Crowdin owns target catalogs.

## Validation

SQLite migration/integration tests cover counted amounts, supported versions, failure/current-day exclusions, immutable retries, interrupted recovery, partially expired days, retention, atomic registration rollback and subsequent account deletion. Reporting/component tests cover UTC boundaries, gaps, small cells, read-only recap limitations and admin access. Preview validation must use local D1 and a disposable local admin; no production write is needed to validate this feature.

## D1 runtime regression

The rolling-metric query resolves its existing primary and secondary groups separately to stay within D1’s expanded-query limit. Both writes for a completed UTC day execute in one atomic D1 batch. A failed group rolls the day back; maintenance does not advance its checkpoint or expire raw events. Live reads request only the required groups and combine their rows. Metric formulas, windows, dimensions and the seven-day backfill limit are unchanged. The nightly backlog budget fixture executes 34 SQL statements and remains within its existing resource gate.

`tests/lib/server/product-metric-runtime.test.ts` runs the actual migrated definitions in an ephemeral local D1 runtime with remote bindings disabled. It verifies all ten metrics, dimensions, matured return cohorts, live reads, rollback on a failed second group, retry, annual totals and raw expiry. This catches the SQL expansion failure that host SQLite alone does not reproduce.
