# Offline PWA evaluation for TrackDraw

Date: October 24, 2026

Status: parked on October 24, 2026 after the maintainer selected Electron for continued desktop development. Source and repository investigation is retained for reference; no PWA has been built or accepted. There is no active PWA prototype or browser-storage migration scope. The [Desktop Workspace PVA](../../pva/desktop-workspace-pva.md) owns delivery.

## Current decision and retained findings

The maintainer chose Electron after reviewing this investigation. PWA implementation is parked and is not a prerequisite for continued desktop development or distribution acceptance. Reconsider it only through a separate decision if Electron maintenance/distribution costs become unacceptable or new user needs justify an alternative.

An offline PWA remains a technically credible alternative for occasional venue editing. TrackDraw already performs editing and rendering on the device. A PWA could reuse that editor and avoid distributing a separate Chromium runtime. Electron deliberately bundles Chromium and Node.js, trading installation size and runtime maintenance for a controlled desktop environment. Neither choice automatically reduces server work or guarantees lower memory use; measure TrackDraw's actual builds. [Electron architecture](https://www.electronjs.org/docs/latest/), [Electron's bundling rationale](https://www.electronjs.org/docs/latest/why-electron).

The decisive distinction is the kind of blocker. A previously cached PWA can serve its editor without reaching the website's network endpoint. It cannot be promised to work around policies that prohibit opening that URL or running the app itself. Retain Electron as the stronger candidate for independence from the normal browser's website-data lifecycle and URL controls, without treating it as immune to device-management restrictions.

## What offline actually requires

Service workers intercept requests and can return locally stored responses. A cache-first or cache-only editor shell can avoid waiting for a DNS lookup, failed connection or remote response when its resources are already present. This makes network independence technically plausible; it is an architectural inference to verify on TrackDraw and the target devices. It is not evidence that every venue filtering product behaves the same. [Google's serving strategies](https://web.dev/learn/pwa/serving), [W3C service-worker fetch/cache model](https://www.w3.org/TR/service-workers/).

The first visit still needs a working connection. Registration, successful activation, the complete required asset set and the project data must exist locally before disconnection. The browser can restart a registered worker when an in-scope request arrives, so an open tab need not be kept alive. Installing an icon alone proves none of the offline requirements: Edge explicitly permits installation without a service worker. Cache construction must be implemented and verified. [Google's service-worker guide](https://web.dev/learn/pwa/service-workers), [Microsoft's PWA guide](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/).

Cache availability should be automatic app infrastructure. Existing locally saved projects must remain ordinary projects, without a separate per-project preparation or pinning step. A cloud-only project never downloaded to this installation still requires connectivity. A clear application-level status can report when the installed version is available offline, without making users manage individual cache entries.

| Venue condition                                                                | PWA expectation after complete prior setup                                                            | Electron alpha expectation                                                                       | Acceptance boundary                                                               |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| No internet; browser/app fully closed first                                    | Cached shell and locally stored projects can cold-start.                                              | Installed bundle and SQLite can cold-start.                                                      | Test actual relaunch, not only DevTools offline in an already open tab.           |
| Wi-Fi online, TrackDraw DNS/TCP access denied or blackholed                    | Cache-first startup should avoid the network dependency.                                              | Local renderer should avoid it.                                                                  | Test timeouts and real network blocking separately.                               |

The browser-policy row is materially different from network failure: Chrome documents URLBlocklist as preventing access, and Chromium's policy navigation throttle can immediately deny navigation. A service worker is not an exception to an administrator's policy. The exact behavior of a particular installed PWA, browser version or extension still needs a test; these sources do not establish a universal interaction matrix. [Chrome policy documentation](https://support.google.com/chrome/a/answer/7532419?hl=en), [Chromium navigation throttle](https://chromium.googlesource.com/chromium/src/+/c1ce99f4ed59/components/policy/content/policy_blocklist_navigation_throttle.h).

## Storage, updates and installation

IndexedDB stores project data; Cache Storage stores the runnable shell/resources. They solve different problems. Browser storage is best-effort unless persistence is granted. `navigator.storage.persist()` is a request, not a guarantee of approval; inspect its return value and `persisted()`. Persistent buckets protect against automatic clearing under the standard, but user deletion and profile/device loss remain possible. Quota errors require a visible save failure and an export/recovery path. IndexedDB is therefore suitable infrastructure, not a substitute for a backup policy. [WHATWG storage standard](https://storage.spec.whatwg.org/).

WebKit supports Storage API persistence from Safari 17 and grants requests using heuristics, including Home Screen use. It also documents origin-level eviction under storage pressure. Avoid the blanket claim that every Safari PWA loses data after seven days: WebKit's current tracking-prevention documentation explicitly exempts the first-party Home Screen web-app domain from that ITP cap. Verify macOS Dock and mobile installation behavior separately; do not generalize the Home Screen exemption into an unconditional retention guarantee. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [WebKit tracking prevention](https://webkit.org/tracking-prevention/).

Updates can download in the background, but deployment still needs engineering. New workers normally wait while the old version controls clients. Immediate `skipWaiting()` can mix running code and new asset behavior. TrackDraw should stage a complete version, retain the current working version on failed download, persist pending edits before a deliberate switch, and keep storage migrations compatible. A blocked update endpoint must not prevent using the installed version. [Google's worker lifecycle](https://web.dev/articles/service-worker-lifecycle), [Workbox update handling](https://developer.chrome.com/docs/workbox/handling-service-worker-updates).

Installation and file workflows need a declared browser/platform matrix. Chrome/Edge offer desktop PWA installation across Windows, macOS and Linux. Safari supports Add to Dock on macOS Sonoma 14+, with website data separate from Safari; existing browser projects must not be assumed to appear in the installed app. Firefox now offers web-app windows on Windows starting with version 143, with Microsoft Store support from 150; this is not universal macOS/Linux installation support. Older articles claiming no Safari or Firefox desktop web apps are inadequate for this decision. [Google desktop installation](https://web.dev/learn/pwa/installation), [Apple web apps](https://support.apple.com/en-gb/104996), [Mozilla web apps](https://support.mozilla.org/en-US/kb/web-apps-firefox-windows).

Keep ordinary file input and downloaded JSON as the portable baseline. Native-style file pickers and save-in-place handles can be a progressive enhancement where supported; permission and browser differences remain. These APIs have a different permission model from Electron's native filesystem capabilities; TrackDraw's existing Electron bridge deliberately exposes only restricted operations. [Chrome file access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access), [Google's file-open fallback](https://web.dev/articles/files/open-one-or-multiple-files), [TrackDraw native bridge](../../../experiments/electron-desktop/main.cjs).

## TrackDraw-specific work

Repository inspection on the desktop JSON branch found no existing service-worker registration, PWA manifest, IndexedDB project layer or persistent-storage request. Current browser storage is synchronous `localStorage` for drafts, named projects and restore points in [projects.ts](../../../src/lib/projects.ts). Caching HTML alone does not make this Next.js application offline-ready.

- [Studio entry](../../../src/app/studio/page.tsx) loads the client editor dynamically. Team/account entry paths and server dependencies need deliberate offline boundaries. Team workspace entry waits for session/server data, and the local project layer intentionally excludes moved team projects: this investigation does not establish offline support for every cloud/team project.
- The shared editor lazily loads 2D/3D code and dialogs. Precache the required chunk graph, locale files, catalog resources and export dependencies, including features never opened before going offline. PDF export also dynamically requests a Chinese font, so first-use Chinese-label export belongs in acceptance. [Locale provider](../../../src/i18n/ClientLanguageProvider.tsx), [catalog](../../../src/lib/track/elements/catalog.ts), [PDF font](../../../src/lib/export/pdf-font.ts), [map provider](../../../src/lib/map-reference/provider.ts).
- [Account sync](../../../src/components/editor/useAccountProjectSync.ts) and `/api/auth` requests must be non-blocking for local work. Test expired sessions, account switching and signed-out local data isolation. Never authorize cloud operations using stale credentials or cache authentication responses to simulate login.
- Apply the existing [deployment cache contract](../../deployment/deployment-setup.md): allowlist public immutable editor resources and a generic unauthenticated offline shell. Do not blanket-cache `/`, `/api/*`, auth, private account responses or published shares. Share revocation/moderation checks remain fresh per request; local project availability does not authorize stale public or private hosted access.
- Keep map metadata and external appearance references while allowing missing imagery. Offline caching rights and provider/resource policies require a separate audit; a service worker does not grant redistribution permission.
- Reuse [project-file validation](../../../src/lib/track/project-file.ts) and the [rich JSON fixture](../../../tests/fixtures/json-roundtrip.json) for equality checks. The current [Electron experiment](../../../experiments/electron-desktop/README.md) is a useful comparator, with a bundled renderer/catalog, native SQLite and macOS smoke evidence. Windows/Linux acceptance remains open.

## Conditional validation if revisited

The following is a retained test proposal, not active delivery work. If PWA work is explicitly reopened, first build an isolated cached editor shell using the existing shared editor and JSON format. Begin with the existing browser project layer to answer cold-start and blocker questions; do not quietly migrate user data. Separately evaluate an IndexedDB adapter behind `src/lib/projects.ts`, with transactional writes, non-destructive migration/rollback, multi-tab coordination and visible storage failures before claiming production durability. Use a separate branch and disposable origin/profile; avoid installing an experimental root worker over production routes.

Run the matrix above on Chrome/Edge desktop, Safari macOS, and representative Android/iOS devices; include Firefox browser use and Windows web-app mode where supported. Record exact versions. For each supported configuration: import the rich fixture, fully quit, block network/auth, relaunch, open previously unused 3D/export features, edit, undo/redo, save, restart and export. Compare all portable data. Test persistence denial, quota failure, deliberate site-data clearing, interrupted update, old-tab/new-version coexistence and recovery. Record startup time, cached/download bytes, memory, update friction and maintenance work against the Electron alpha.

Choose PWA as the primary optional offline offering only after these scenarios pass for the declared target matrix and users accept the storage/installation limits. Keep Electron if dependable local app startup/file handling or independence from browser origin lifecycle is decisive, or PWA failures affect real venue users. A PWA may still improve browser continuity even when Electron remains available. These are conditions for a future reconsideration, not a current instruction to run the experiment. Electron remains the selected direction; neither runtime is promised to defeat every website blocker.
