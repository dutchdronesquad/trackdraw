# Durable Objects Resource Evaluation

Status: architecture research, checked 2026-11-02. A subsequent [local team-project transport comparison](../in-progress/team-project-transport-comparison.md) includes isolated prototypes, measured local operation counts, and a single-query conditional polling implementation prepared for review. Durable Objects remain experimental. No deployment, hosted traffic measurement, or demonstrated production savings. Recommendations below are engineering judgments based on the current checkout and official documentation.

## Recommendation

Durable Objects (DOs) are a credible coordination layer for team-project update notifications, but are not a general replacement for D1, caching, or scheduled cleanup. First measure and compare a smaller revision/status endpoint with conditional project fetching and visibility-aware polling. If that is insufficient, evaluate one hibernating WebSocket room per project while retaining D1 authorization, project revisions, and edit leases as the safety boundary.

Do not start with full co-editing, analytics migration, or a DO for every account. The existing [collaboration evaluation](real-time-collaboration-evaluation.md) covers the separate shared-document and undo questions; push notifications about a saved revision do not solve them.

## Platform and cost boundaries

New classes should use SQLite. Current [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) states:

| Meter               | Workers Free    | Workers Paid                                        |
| ------------------- | --------------- | --------------------------------------------------- |
| Requests            | 100,000/day     | 1 million/month included; $0.15/million overage     |
| Duration            | 13,000 GB-s/day | 400,000 GB-s/month included; $12.50/million overage |
| SQLite rows read    | 5 million/day   | 25 billion/month included; $0.001/million overage   |
| SQLite rows written | 100,000/day     | 50 million/month included; $1/million overage       |
| SQLite storage      | 5 GB total      | 5 GB-month included; $0.20/GB-month overage         |

Free limits reset at midnight UTC; exceeding a meter rejects corresponding operations. Paid metered overage rounds upward to billable units. Workers Paid has a $5/month minimum; caller Worker charges are additional. HTTP/RPC calls, alarms, and WebSocket upgrades count; incoming WebSocket messages use a 20:1 billing ratio, outgoing messages do not. Allocated memory is billed as 0.128 GB per active object. Deletes and `setAlarm()` count as writes. These are published prices, not TrackDraw's observed bill or available account allowance. [Pricing and examples](https://developers.cloudflare.com/durable-objects/platform/pricing/)

Relevant [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/): 100 classes on Free / 500 Paid, unlimited object count, a soft 1,000 requests/second per single-threaded object, received WebSocket messages up to 32 MiB, SQL row/string/blob up to 2 MB, and default 30-second CPU limit configurable up to five minutes. Shard by coordination entity, never through one global application object. Large design snapshots should remain in their current persistence path rather than becoming WebSocket presence messages.

Do not extend that DO CPU table to the caller Worker: [Workers HTTP limits](https://developers.cloudflare.com/workers/platform/limits/#cpu-time) are 10 ms on Free and 30 seconds by default on Paid, configurable to 300 seconds on Paid. The DO page also says Workers plan limits apply without clearly reconciling its unqualified 30-second table; confirm Free DO CPU enforcement before designing CPU-heavy Free workloads.

**Documentation uncertainty:** the limits table lists 10 GB per SQLite object without a plan qualifier, but its storage-full FAQ says 10 GB Paid / 1 GB Free. Free account total is consistently 5 GB. Conservatively design below 1 GB/object on Free and verify the actual account limit before sizing. The pricing page also retains future-tense January 2026 storage-billing language; do not infer storage is currently free from that wording. Its limits FAQ loosely conflates I/O and compute, whereas pricing explicitly bills active wall time; use the pricing/lifecycle definition when estimating duration. [Limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## Hibernation, failures, and consistency

Use `ctx.acceptWebSocket()` and class message handlers, not ordinary `ws.accept()` listeners. Hibernation preserves connected clients but discards object memory and reruns the constructor on wake; reconstruct connection metadata with attachments and important state from storage. It is not a guarantee against disconnects. [WebSocket guidance](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

Static application ping/pong can use `setWebSocketAutoResponse()` without waking the object or adding duration. This establishes transport liveness only: it cannot renew an authorized edit lease, check revoked permissions, or perform mutable business logic. [Auto-response API](https://developers.cloudflare.com/durable-objects/api/state/#setwebsocketautoresponse)

Timers, unfinished requests/I/O, pending `waitUntil()` promises, outbound connections, and standard WebSockets prevent hibernation. Billing stops when an idle object becomes eligible, without waiting for actual eviction. Avoid per-room intervals and long polling inside the DO. Runtime restarts/code updates can terminate WebSockets: clients need jittered reconnect, fresh authorization, revision reconciliation, and a bounded polling fallback. [Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)

One DO has one scheduled alarm; a stored due-event queue can multiplex deadlines. Alarms execute at least once and retry thrown failures up to six times with exponential backoff starting at two seconds. Make handlers idempotent, persist progress, and monitor exhausted delivery rather than treating them as unlimited retry or exactly-once execution. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)

For ordinary DO calls, retry only suitable `.retryable` failures with idempotent operations and backoff, recreate a broken stub, and do not retry `.overloaded` errors. A client losing the response does not establish that a mutation failed; operation IDs and revision checks must prevent duplicate effects. [Error handling](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/)

D1 and DO storage are separate consistency domains. DO local storage ordering does not make a D1 save and a room broadcast atomic; external I/O permits event interleaving. D1 batches provide a transaction for D1 statements, not for a DO call. [DO concurrency rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/), [D1 batches](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

For an initial team pilot:

1. Keep existing D1 authorization predicates, revision compare-and-swap, lease expiry, and session matching. A room conveys revision hints; it does not grant edit ownership.
2. If reliable notification delivery is required, record a revision/event outbox with the D1 save and dispatch it after commit. A successful D1 commit followed by failed DO delivery must remain recoverable through outbox retry and client reconciliation. Deduplicate broadcasts and ignore old revisions.
3. Fetch authoritative content after reconnect or an uncertain/gapped sequence. A periodic bounded reconciliation path is still necessary; count its requests.
4. Revalidate access for new connections and protected operations. Long-lived sockets require an explicit invalidation/bounded reauthorization design for membership removal, role changes, account bans/deletion, token/consent revocation, and project archival. A valid attachment is not perpetual authorization.
5. Do not run mixed DO-owned and D1-owned lease authorities. Moving leases later requires a separate fencing/migration/rollback design covering delayed saves and successor ownership.

For asynchronous delivery without online coordination, compare Queues with durable D1 job state. Queues is also at least once and needs idempotency; it does not close a D1-commit/enqueue gap by itself. [Queue delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)

Any buffered analytics proposal must preserve existing consent and session/account deletion behavior in [product events](../../../src/lib/server/product-events.ts), and prove equivalent ordered/distinct metrics before discarding raw history. Delayed buffers must not reintroduce deleted data. [Embed-referrer counters](../../../src/lib/server/embed-referrers.ts) check share eligibility in their write path; a flush must recheck current deletion/revocation/publication state rather than resurrect counters from an earlier authorized event. Identifier-free localization demand is a separate measurement purpose, not a reason to merge these streams. Review [privacy](../../../src/app/privacy/page.tsx) and [terms](../../../src/app/terms/page.tsx) if an eventual implementation changes data collection, retention, or user-facing live sessions.

## Integration and alternatives

[OpenNext explicitly supports custom Worker exports for Durable Objects](https://opennext.js.org/cloudflare/howtos/custom-worker). TrackDraw already has a [custom Worker](../../../custom-worker.ts), so no framework migration is indicated. A future proof would add a class export, SQLite class migration and namespace binding, independently configured development/production namespaces, environment types, and a narrowly scoped authenticated upgrade route while preserving current guards, scheduled handler, and generated OpenNext fetch delegation. Current [Wrangler configuration](../../../wrangler.jsonc) contains no DO binding. This is architectural feasibility, not verified adapter/runtime behavior. Validate through `npm run preview` and the [deployment guide](../../deployment/deployment-setup.md) before any rollout.

Do not put public assets, static shells, gallery responses, or share snapshots behind a DO merely to cache them. [OpenNext configuration](../../../open-next.config.ts) already selects a static-assets cache for public shells. The [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) is data-center-local and executes within a Worker; edge caching that avoids Worker execution is a separate option. Cache invalidation and share expiry/revocation remain explicit product constraints. D1 query reduction, response projection, indexes, conditional requests, and visibility-aware polling should be baseline comparisons, not skipped because DOs are available.

The React `cache()` wrapper in [share page data](../../../src/lib/server/share-page-data.ts) deduplicates within a render request; it is not a cross-request response cache. Any future public share cache needs a deliberate expiry/revocation contract around current share resolution.

Prefer Cron plus indexed due-time queries and bounded batches for broad retention. Alarms are better justified for entity-local deadlines or existing room cleanup, not thousands of idle objects invented solely to replace 73 scheduled invocations/day. Measure rows scanned, backlog, and retry behavior, not invocation count alone. For abandoned DO state, define deletion/retention and use `deleteAll()` for full removal; closing sockets does not erase stored data. [DO cleanup guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#clean-up-storage-with-deleteall)

## Measurement plan and decision gates

Record a representative baseline by route and action: Worker invocations, CPU p50/p95, response bytes, D1 statement latency and `rows_read`/`rows_written`, errors, client refresh delay, active projects/viewers/editors, and reconnect rates. Separate full-project reads, authorization reads, lease renewals, saves, budget writes, and cleanup scans. Do not derive billable rows from SQL statement count. Existing [MCP CPU research](../in-progress/mcp-request-cpu.md) demonstrates why smaller payloads can still read more rows.

Illustrative accounting, not a forecast:

| Synthetic scenario                                                     | Baseline arithmetic                                                                                                                              | Proposed comparison                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One project, one editor, four viewers, one hour                        | At 20-second intervals: approximately 720 viewer refreshes plus 180 lease renewals; initial loads, focus events, retries, and saves add traffic. | Compare (A) current behavior, (B) small revision/status polls with conditional full fetch and hidden-tab suspension, (C) five room connections plus actual revision notifications, reconciliation and unchanged D1 renewals.                                                                  |
| Five clients send one application message every 20 seconds for an hour | 900 incoming messages.                                                                                                                           | Roughly 45 request-equivalents plus five upgrades; add DO notifications from saves, authorization/reconciliation, alarms, and reconnects. Count application heartbeat messages unless their billing treatment is explicitly confirmed; auto-response duration avoidance alone is established. |
| One ordinary WebSocket room held active for one hour                   | `3,600 × 0.128 = 460.8 GB-s`; concurrent clients share that room's duration.                                                                     | If measured non-overlapping active handlers total 30 seconds and the object is otherwise hibernation-eligible: `30 × 0.128 = 3.84 GB-s`. I/O and other activity increase that assumption.                                                                                                     |
| 1,000 authorized MCP calls across multiple budget keys                 | Approximately 1,000 accepted budget upserts plus authentication work.                                                                            | Exact durable DO budgets add about 1,000 RPC requests and durable counter updates; compare whole-path latency/contention and combined storage/compute rather than claiming writes disappear.                                                                                                  |

Apply pricing to monthly account-wide totals after included allowances and rounding, not independently to each scenario; include caller Worker, retained D1 work, DO storage, outbox traffic, and operational overhead. Free daily limits need separate burst analysis. Use 1/10/100 concurrent rooms with idle, burst-editing, mobile background/resume, and reconnect-storm profiles.

Before selecting a pilot, require:

- A measured bottleneck and a comparison showing DOs improve the chosen resource or freshness target beyond simpler polling/query changes; choose the target and acceptable latency/error budget before testing.
- No loss of lease exclusivity, revision safety, local recovery, or authorization during member removal, account ban/deletion, token revocation, two-tab races, delayed saves, restart, failed D1 commit, or failed post-commit notification.
- Demonstrated hibernation under idle connections, bounded per-room storage, acceptable reconnect load, and visibility of duration, overloads, alarm exhaustion, outbox backlog, and retained D1 costs.
- A safe feature-flagged fallback to D1 reads/leases, independently isolated development state, preview validation, and a documented rollback that does not create two write authorities.

Decision order: measure and simplify team polling first; consider a project update room second; examine MCP budget coordination only if measured contention remains; defer notifications, analytics buffering, and per-entity cleanup until their own workload/product evidence warrants them.
