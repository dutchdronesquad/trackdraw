# Personal And Team Projects

Implementation contract for [#1021](https://github.com/dutchdronesquad/trackdraw/issues/1021), [#1022](https://github.com/dutchdronesquad/trackdraw/issues/1022) and [#1023](https://github.com/dutchdronesquad/trackdraw/issues/1023), under the [teams epic](https://github.com/dutchdronesquad/trackdraw/issues/1018).

## Studio workflow

Projects → Account shows personal projects and teams in a compact desktop navigation column with initials. Mobile and tablet use the existing shadcn Select for the same locations. Project rows remain flat and show their last change; the primary creation action belongs to the selected location. Selection is persisted by account ID in `trackdraw.projectLibrary`; it contains no designs. Team pages use bounded metadata reads with cursor pagination, live membership checks and no-store responses. Personal/device/snapshot/shared-link flows retain their current behavior. Missing membership falls back to personal projects on reload/focus. Switching accounts remounts the list and ignores old in-flight responses.

Owners/editors can create a blank version 2 project in an explicitly selected team; viewers cannot. Each project has exactly one owner and independent creator provenance. Opening `/studio?teamId=…&teamProject=…` starts read-only; viewing/export never claims a lease. Owners and editors explicitly choose Edit project, while other tabs see the editing member's name. Even two tabs of the same account are independent sessions. A compact context bar shows team/project identity and the single live save/session status. Finish editing is a quiet text action. Projects saves pending changes and releases the session before navigating; a failed save keeps the recovery draft on screen. Mobile retains a compact export action.

## Exclusive editing and recovery

`POST /api/team-projects/editing` accepts acquire, renew, release and save using the authenticated browser actor and same-origin CSRF check. A server-generated random session ID is returned only to the acquiring tab, never in project reads. Acquisition is a single conditional SQL upsert; a live lease cannot be replaced. Every new lease fetches the current server design and revision before mounting the editor. Leases last 90 seconds according to SQLite's statement-execution clock, with a 20-second heartbeat; expired tokens cannot renew themselves. The client stops editing conservatively after 75 seconds without successful renewal and on an offline event or failed write/renewal. Requests time out after 12 seconds. Throttled/background tabs must reload and acquire a new session if their lease expires.

Every design UPDATE checks current owner/editor membership, team ownership, archive state, expected revision and the actor/project/session/expiry tuple in the same statement. Revision conflicts never force-write. Saves are serialized and deferred during active pointer interactions. Finish editing saves pending changes before releasing; a failed save preserves the draft instead of handing it off. Pagehide/unmount releases are best effort, bound to the old session token; a late release cannot delete a successor's session. Crashes recover through bounded expiry. Personal REST/MCP writes and archive remain personal-only and cannot bypass the team boundary. Existing ownership moves reject active leases; team lifecycle and credential routes use this same table and revision guard.

Private content never hydrates or autosaves into personal drafts, restore points or account synchronization. In-session undo/redo stays available while editing. Losing the lease freezes editing and preserves any unsaved design in memory for explicit JSON export. Reload explicitly discards that draft and fetches the latest server version; it never replays the old draft. A reload/crash can lose an unexported in-memory draft, and navigation/unload warns while changes remain unsaved. Membership is checked on every mutation/renewal and read-only views revalidate on focus/visibility and every 20 seconds. Failed read authorization/network verification clears the displayed canvas and history. Account changes immediately hide old content, including recovery exports. Publication actions are available only to the team owner after finishing editing; published snapshots remain unchanged by edits.

## Deliberate personal-to-team move

A personal owner can move a project into a team they own. The active personal project must finish synchronization first. The confirmation names the destination and describes member access, removal of this device's personal cache/history, absence of reverse transfer and the existing share/gallery exposure. It reads current revision and a hash of publication state before enabling confirmation.

A single conditional SQL UPDATE checks personal ownership, expected revision, current destination owner membership, active archive status, absence of an unexpired editing lease, and the exact publication snapshot. The update preserves project ID, design JSON, creator and appearance references, clears the personal owner, sets the team owner and increments revision exactly once. A concurrent save, publication change, membership loss or second move causes a safe conflict. Old personal saves, force-overwrites and MCP proposals cannot write through the team ownership boundary. Team-to-personal and team-to-team transfers are not supported.

Migration `0032_project_edit_leases.sql` establishes `project_edit_leases(project_id, user_id, session_id, expires_at)` as the shared ownership-change guard. The editing endpoint uses this same table for acquisition, renewal, release and writes; `0033_project_edit_lease_guards.sql` invalidates tokens on membership removal/role changes (even if permissions are restored before expiry) and guards archive/ownership changes at the database boundary.

Existing published snapshots, canonical `/share/[token]` links and gallery entries are preserved with their original publisher. A move does not revoke or make existing public content private, and makes publication management available to the current team owner. The confirmation states this explicitly. Active link/gallery counts and changes to revoked/expired/gallery states are included in preview/confirmation validation; raw tokens are not returned in the preview.

After a successful move, the personal cache, matching draft and restore points are removed through `src/lib/projects.ts`. A persistent ID-only ownership marker blocks late writes/restore points from old tabs from recreating that personal cache. An explicitly created copy has a different ID and remains personal. The page then reloads into an authorized read-only team workspace, cancelling personal synchronization timers. No team content is stored in account/device drafts or restored across identities.

## Deliberate public snapshots

The team owner opens Share from the read-only workspace, after saving and finishing editing. The existing sharing dialog explains link audience, downloading/copying, gallery discovery and the limits of revocation before publication. Multiple retained links can be selected and managed separately. Copying a link or changing membership never republishes the design. Publishing/updating uses the saved server design and an expected revision, with the live owner membership check in the same SQL statement. A stale revision requires reloading the workspace before publishing again.

`/api/team-projects/publication` is browser-session-only, same-origin for writes, no-store/Vary: Cookie and bounded to 4 KiB commands. It rejects client-supplied designs and preview uploads. The snapshot contains rendering geometry, explicit title/description, canonical public catalog identities, public timing markers and registry artwork references. It excludes map reference data, inventory counts, account/team identifiers, draft state, arbitrary internal metadata and private appearance identifiers. Private appearances use standard rendering instead; this provides no artwork-library or reuse grant. Team gallery entries use the standard fallback preview rather than uploading a private editor canvas.

Canonical `/share/[token]` links, embeds and gallery destinations resolve only stored snapshots. An internal save does not update that snapshot; only the explicit Update link action does. Unlisting removes gallery discovery while retaining the active link. Revoking makes the snapshot unavailable and removes its gallery entry. Moderation-hidden listings cannot be relisted or edited by an owner. Existing personal/anonymous sharing remains supported. Generic share/gallery mutation statements also check the current project owner or team-owner membership, so historical publisher identity cannot bypass current permissions. Personal publication writes reject projects moved to a team, including ownership changes between request authorization and the write.

Membership removal does not revoke deliberate public links; their management uses current team-owner membership. Existing account-deletion guards prevent team owners from deleting their account. Team ownership transfers through the existing `/api/teams` command boundary to one accepted, verified member; the previous owner becomes an editor. Public-share and gallery attribution moves to the new owner in the same atomic statement. Creator/member departure or personal-account deletion leaves team projects with the team. Owner accounts remain excluded from inactivity deletion. Team deletion requires an impact review and exact-name confirmation, and rejects a changed review. It immediately cancels invitations, invalidates editing leases, removes public shares/gallery entries and permanently purges that team’s projects and membership records; media cleanup uses the existing durable work queue. There is no team trash/restore period. Previously downloaded/exported copies cannot be recalled.

## Validation and rollout

Run lint, typecheck, tests, build and i18n checks. Apply local migrations and use the Cloudflare preview for authenticated member/outsider, create, move, read-only, export, navigation and mobile checks. The SQL-backed tests cover role isolation, metadata-only pagination, concurrent moves, revision/publication races, leases and personal credential isolation. Component/storage regressions cover account-switch late responses, membership fallback and stale personal cache writes.

The generalized privacy/terms text was reviewed: it already covers membership/access roles, hosted project content, user-controlled visibility, explicit publication and content ownership. This slice does not require another feature-specific legal paragraph. Development deploys follow main; production remains release/manual. No remote migration or deployment is part of local validation.

## Individual integrations

REST and MCP can address a team only through explicit consent and context. API keys select one personal/team context plus all/selected projects; MCP requires the optional `teams:access` scope and `team_id` per call. Existing grants remain personal. Every read/write intersects that grant with live membership and role. Owner/editor mutations use the same revision guard and exclusive editing lease as Studio. Pending proposals retain their original context and recheck access on apply. See [API access](../api-key-project-access.md) and [MCP](../mcp.md). Publication remains owner-only through the existing Studio flow.
