# @trackdraw/viewer

Extracted, framework-neutral 2D/3D track viewer. `TrackViewer` takes a plain `design` prop, has no dependency on the editor's Zustand store, `next-intl`, or `next/navigation`.

See [Track Viewer Package PVA](../../docs/pva/track-viewer-package-pva.md) for the phase plan:

- Phase 1 (issue [#859](https://github.com/dutchdronesquad/trackdraw/issues/859)) proved extraction, finalized the display-metadata allowlist (`src/snapshot/`), and fixed the eager whole-catalog texture preload.
- Phase 2 (issue [#860](https://github.com/dutchdronesquad/trackdraw/issues/860)) added `package.json`, the ESM + static builds (`npm run viewer:build` from the repo root), the asset manifest (`src/assets/manifest.ts`, generated by `scripts/generate_viewer_asset_manifest.mjs`), schema-validated snapshots (`src/snapshot/schema.ts`), and the shared snapshot builder's first two real callers (the editor's "Viewer Snapshot" export action and `GET /api/v1/projects/[projectId]/viewer-snapshot`).

**Not published to npm.** This package builds (`dist/`) but nothing publishes it to a registry yet — that's deferred to whenever a real consumer (Phase 3's DDS site or Phase 5's RotorHazard plugin) needs an installable version. The app itself consumes this package's _source_ directly via a dev-only TypeScript path alias (`@trackdraw/viewer`, see the root `tsconfig.json`/`vitest.config.ts`), not the built `dist/` output.

The package stays in this repository (an npm workspace, `packages/viewer`) through Phase 1 and Phase 2 — this is not a permanent commitment, but a split is not planned unless a real publish pipeline makes one clearly worth it.

## Builds

`npm run viewer:build` (from the repo root) produces:

- `dist/*.js` — ESM build, multi-entry (`.`, `./mount`, `./snapshot/*`, `./assets/*`) so server code can import light subpaths without pulling in React/three/konva.
- `dist/static/trackdraw-viewer.global.js` + `dist/static/trackdraw-viewer.css` — a self-contained IIFE bundle (`window.TrackDrawViewer`) plus a compiled Tailwind stylesheet, for hosts with no npm/bundler of their own (e.g. a future RotorHazard plugin). Load both:
  ```html
  <link rel="stylesheet" href=".../trackdraw-viewer.css" />
  <script src=".../trackdraw-viewer.global.js"></script>
  <script>
    const handle = TrackDrawViewer.createTrackDrawViewer(container, { design });
  </script>
  ```
- ESM/React consumers use `createTrackDrawViewer` (or the `<TrackViewer/>` component) from `@trackdraw/viewer` directly and are expected to already run Tailwind; they can optionally load the same `trackdraw-viewer.css`.

**Known gap:** the ESM build ships **no `.d.ts` type declarations**. `tsup`'s `dts` option auto-installs a pinned `rollup-plugin-dts` that isn't compatible with this repo's TypeScript 7 (crashes on an internal Compiler API change). Not a blocker today (nothing consumes `dist/` yet), but needs revisiting before any real npm publish — see the comment in `tsup.config.ts`.

**Source imports reach into the app.** `src/**` has `@/...` imports into the main app's `src/` (hooks, renderers, catalog logic) — a deliberate Phase 1/2 shortcut (bundled via alias resolution at build time, see `tsconfig.json`'s `paths`), not yet vendored into a self-contained source tree. Flagged for a future extraction pass, not required by anything currently in scope.

A chrome-less host page exercising this package lives at `src/app/dev/viewer-spike/` in the main app.
